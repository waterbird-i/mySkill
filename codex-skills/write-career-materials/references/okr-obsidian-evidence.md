# OKR / 述职 / 面试材料证据路由

Use this reference when the target material depends on the user's recent work history rather than a single provided project brief.

## Evidence Priority

1. User-provided target and date range.
2. Local Obsidian sources:
   - `comate-stack/OKR.md`
   - `baidu/周报/YYYY/`
   - `baidu/日报/`
   - `工作/my/职称评定-*.md`
   - `工作/my/简历项目介绍-*.md`
   - existing interview or project-experience directories
3. Git evidence from the relevant repos, filtered by author and date range.
4. Codex Memories and rollout summaries for cross-session context.
5. Chronicle only as a clue source; confirm important facts in files, Git, or thread summaries before using them.

## Workflow

1. Identify the output type.
   - OKR review: map evidence to objective / KR structure.
   - Monthly self-report: map evidence to delivery story and user/organization impact.
   - Project experience: map evidence to contribution, difficulty, solution, benefit, and reusable assets.
   - Interview answers: map evidence to question clusters and concrete examples.
2. Build an evidence ledger before drafting.
   - Date / source / fact / impact / confidence / missing metric.
   - Keep raw file paths or commit refs so claims are traceable.
3. Translate facts into capability language.
   - Feature work -> capability.
   - Bug fix -> reliability or governance mechanism.
   - Repeated workflow -> operating model or reusable asset.
   - Tooling/setup -> productivity or delivery-risk reduction.
4. Draft only after the ledger has enough support.
   - If evidence is thin, write a conservative version and mark missing metrics.
5. End with a gap list.
   - Metrics to ask the user for.
   - Claims that need repo or source confirmation.
   - Follow-up docs that should be created separately.

## Stop Conditions

- The requested artifact is drafted with traceable evidence.
- Missing evidence is explicitly marked instead of invented.
- The final text avoids commit-log language and explains impact in user or organization terms.
