# 证据驱动写作工作流

## 1. 先收证据，不先写句子

每个项目先整理成下面这 8 格，缺哪格就显式标记缺口：

1. `项目定位`：它解决什么关键问题，为什么值得写。
2. `影响范围`：用户数、团队数、端数、链路长度、业务关键性。
3. `核心矛盾`：旧方案为什么不行，真正难点是什么。
4. `关键判断`：为什么选这条路线，不选别的路线。
5. `方案机制`：分层、协议、治理、调度、闭环、迁移、观测、复用。
6. `个人职责`：你拍板了什么、主导了什么、扛住了什么。
7. `结果指标`：规模、质量、效率、复用、影响范围。
8. `长期资产`：平台、规范、模板、FAQ、监控、评测、方法论。

## 2. 抽象提升规则

把低层事实往上翻译一层，再决定是否继续上提：

- 做了页面/接口 -> 建设了某项能力
- 修了一个问题 -> 建立了某套治理机制
- 写了脚本/工具 -> 沉淀了复用资产
- 接了一个场景 -> 打通了端到端闭环
- 完成了一次发布 -> 支撑了规模化交付/迁移
- 优化了某项指标 -> 提升了产品竞争力/稳定性/组织效率

如果上提后失真，就退回原层，不要硬拔高。

## 3. 职称评定写法

职称评定优先写“级别证明”。

推荐骨架：

1. 项目一句话定位
2. 背景与核心矛盾
3. 关键判断与方案取舍
4. 方案设计与机制建设
5. 个人职责
6. 项目业绩
7. 长期沉淀

写法要求：

- 每个项目只抓 1-3 个核心矛盾。
- 必须出现“为什么这样设计”的句子。
- 必须解释指标意味着什么，而不是只堆数字。
- 必须让读者看出你的角色边界，不要把团队成果全部写成个人成果。

## 4. 简历项目介绍写法

简历项目介绍优先写“筛选效率”。

压缩顺序：

1. 先保留项目定位和最强结果。
2. 再保留关键判断或核心机制。
3. 最后补个人职责和影响范围。

推荐形式：

- 一段版：70-140 字，适合中文简历。
- Bullet 版：3-5 条，每条只写一个高价值信息。

简历里尽量少写：

- 太长的背景铺垫
- 细碎实现过程
- 无法一眼读懂的内部名词

简历里必须写：

- 你负责了什么
- 项目产生了什么变化
- 这个变化为什么稀缺

## 5. 述职/项目介绍写法

述职介于职称评定和简历之间，既要讲故事，也要讲结果。

推荐顺序：

1. 为什么要做
2. 最难的矛盾是什么
3. 你做了什么关键判断
4. 结果如何
5. 留下了什么可复用资产

如果用于口头表达或 slide 文案，句子要更短，术语更少。

## 6. 结果指标的解释方法

不要只写“提升了 20%”，要补一句这个数字说明什么：

- 采纳率提升 -> 用户把能力纳入主流程
- 成功率提升 -> 系统从试验态进入可规模使用态
- 耗时下降 -> 人效或稳定性交付有实质改善
- 覆盖范围扩大 -> 方案具备平台价值或迁移价值

## 7. 自检清单

成稿前逐项检查：

- 有没有先证明这件事值得写？
- 有没有讲清楚真正的难点？
- 有没有出现关键判断，而不只是实现过程？
- 有没有把工作写成能力/机制/治理/平台，而不是功能列表？
- 有没有清晰写出个人职责？
- 有没有量化结果，或显式标出缺失指标？
- 有没有解释长期资产或后续杠杆？
