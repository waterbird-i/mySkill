# Write Career Materials

## Overview

将原始项目事实改写成“可用于评审、简历、述职”的职业材料，不写成功能流水账。
先抽证据，再抬抽象层级，再选写法风格，最后按目标载体成稿。

## Workflow

1. 判定目标载体。
   - 职称评定：允许展开背景、矛盾、判断、方案、职责、业绩、沉淀。
   - 简历项目介绍：压缩到 1 段或 3-5 条 bullet，只保留最能证明级别的事实。
   - 述职/项目介绍：保留故事线，强调阶段目标、结果和组织影响。
2. 建立证据账本。
   - 至少抽出 8 类信息：问题、重要性、核心矛盾、关键判断、方案机制、个人职责、结果指标、长期资产。
   - 若材料缺指标，不要编造；显式留下 `[待补：用户数/采纳率/耗时下降/成功率]` 之类占位。
   - 若只有功能列表，先改写成“能力/机制/治理/平台/迁移/方法论”再继续。
3. 提升抽象层级。
   - 功能 -> 能力
   - 项目 -> 平台/体系
   - 修问题 -> 治理
   - 上线 -> 规模化落地/迁移
   - 实现细节 -> 关键判断与边界取舍
   - 单次事故 -> 可复用方法论
4. 选择风格。
   - 默认先用平衡写法：背景/矛盾 -> 判断 -> 方案 -> 职责 -> 结果。
   - 如果用户点名某个人或某类风格，读取 `references/style-personas.md`。
   - 如果当前机器上存在 `/Users/liancong/Obsidian/工作/2026.5/职称评定*.md`，并且需要更像原稿，优先再读对应原文。
5. 成稿并自检。
   - 每个项目都要能回答：为什么重要、为什么难、为什么是你、为什么这条路线更优、结果说明了什么。
   - 删除“参与了、支持了、协助了”这类弱表述；除非事实确实如此。
   - 优先使用“主导、负责、设计、推动、统筹、打通、建设、沉淀、治理、升级”。

## Output Rules

- 只写用户能自证的事实与结论；对“意义”的提升必须能回指到原始证据。
- 不要把所有功能点都写进去；每个项目只保留 1-3 个最能体现级别的核心矛盾。
- 结果优先写组合指标，而不是单一数字。常见维度：规模、质量、效率、复用、影响范围。
- 职称评定优先突出“判断 + 体系 + 长期资产”；简历优先突出“结果 + 职责 + 稀缺性”。
- 如果项目天然偏底座，必须把它和业务节奏、用户规模或组织杠杆连起来，避免写成后台琐碎工程。

## Deliverable Preference

- 默认直接输出成稿，不先给空泛建议。
- 如果用户要求“模仿某个人”，先给该风格版本；必要时再补一个更平衡的版本供比较。
- 如果事实明显不足以支撑高级表述，先列出缺口，再用最保守的版本成稿。
